# keb — publishing runbook

How `keb` gets from a git tag to `brew install keb`, `npm i -g keb`, and `cargo add keb`.

Written in Rust, distributed everywhere. The language choice and the distribution
channels are independent decisions — this document is about the second one.

## The shape

One tag triggers one CI workflow that fans out to every channel:

```
git tag v0.1.0 && git push --tags
        │
        └─► GitHub Actions (.github/workflows/release.yml, generated by dist)
              ├─ plan
              ├─ build-local-artifacts   cross-compile 5 targets
              ├─ build-global-artifacts  installers, npm packages
              ├─ host                    GitHub Release + checksums
              ├─ publish-homebrew-formula → frycz/homebrew-tap
              ├─ publish-npm              → @frycz/keb + 5 platform packages
              └─ announce

cargo publish  ← MANUAL. dist does not publish to crates.io.
```

Binaries are never built by hand — cross-compiling macOS, Linux and Windows locally
is a problem you never need to have. **crates.io is the exception**: `dist` handles
binary distribution only, and generates no `cargo publish` job. Either run it by hand
on each release, add a step to the workflow yourself, or adopt `release-plz`, which
does own that piece.

## Gatekeepers

There are almost none. Worth knowing exactly which, so the launch is not planned
around an approval that does not exist.

| Channel | Account | Review | Notes |
|---|---|---|---|
| **crates.io** | GitHub OAuth + **verified email** | none | Names first-come, **permanent**. Versions immutable. |
| **npm** | npm account + verified email | none | Names first-come. `keb` is squatted, so we ship scoped — see Names. |
| **Homebrew tap** | **none** — it is a git repo | none | No registry, no login. `brew` clones a GitHub repo. |
| **homebrew-core** | — | **PR review** | Notability bar (~75 stars, or ~30 forks/watchers). Later-stage, optional. |
| **GitHub Releases** | GitHub | none | |

Email verification on crates.io is the only identity check anywhere in this stack.
No code is audited, sandboxed, or read by a human on any of the self-serve channels.

## Repos

Two, and the tap is *not* named after the tool.

```
github.com/<user>/keb             ← public. source, CI, releases
github.com/<user>/homebrew-tap    ← public. one generated .rb file
```

The tap is a *collection* of formulas, not one formula:

| Repo name | Install command |
|---|---|
| `homebrew-tap` | `brew install <user>/tap/keb` ✅ |
| `homebrew-keb` | `brew install <user>/keb/keb` ❌ stutters, one repo per tool |

`homebrew-` is a required prefix; Homebrew strips it. The tap repo contains only
`Formula/keb.rb`, force-pushed by CI on each release — treat it as build output,
never hand-edit.

**The source repo must be public before the first real release.** Homebrew formulas,
the curl installer, and `cargo binstall` all fetch GitHub Release assets by URL, and
assets on a private repo require auth that `brew` will not have. It can stay private
during development; flip it in Settings → General → Change visibility. Scan the
history for anything you do not want public first — flipping exposes the whole log.

## One-time setup

### 1. Names — settled

Checked 2026-09-23:

| Registry | Name | Status |
|---|---|---|
| crates.io | `keb` | free ✅ |
| npm | `keb` | **taken** — a squatter stub at `0.0.0`, bare `index.js`, published once |
| npm | **`@frycz/keb`** | what we ship ✅ |

The npm squat is dead but npm will not hand the name over casually; their name-dispute
process exists for this and is slow with no guaranteed outcome. Not worth blocking on,
because **the package name and the binary name are independent**:

```jsonc
{ "name": "@frycz/keb", "bin": { "keb": "bin/keb" } }
```

Users type `npm i -g @frycz/keb` once, then `keb` forever. Crate name, binary name,
Homebrew formula and repo all stay `keb`; only the npm install string is longer. If
the dispute is ever granted, republishing unscoped is additive.

Every platform package is scoped too: `@frycz/keb-darwin-arm64`, etc.

Re-verify before the first publish, since squatters occasionally lapse:

```sh
curl -s https://crates.io/api/v1/crates/keb -H "User-Agent: name-check (you@example.com)"
npm view @frycz/keb       # E404 means free
```

### 2. Accounts

- **crates.io** — sign in with GitHub, then **verify your email** in settings.
  Publishing is refused until you do.
- **npm** — `npm adduser`, verify email, enable 2FA.
- **Homebrew** — nothing. There is no Homebrew account.

### 3. Create the tap

```sh
gh repo create homebrew-tap --public --description "Homebrew formulas"
```

Leave it empty. `cargo dist init` asks for its name and CI populates it.

### 4. Credentials

**Prefer Trusted Publishing everywhere.** Both crates.io and npm accept GitHub
Actions OIDC: CI proves its identity to the registry per-run and receives a
short-lived token, so no long-lived credential is stored in the repo at all. npm's
token creation form now actively warns against tokens for CI and points here.

Only one long-lived secret is genuinely unavoidable:

| Secret | What | Why it must exist |
|---|---|---|
| `HOMEBREW_TAP_TOKEN` | fine-grained GitHub PAT — `homebrew-tap` only, Contents: read+write | The workflow's built-in `GITHUB_TOKEN` is scoped to the repo it runs in and cannot push to a *different* repo. **Most common first-release failure.** |

| Not needed | Instead |
|---|---|
| `CARGO_REGISTRY_TOKEN` | crates.io Trusted Publishing, configured on the crate settings page |
| `NPM_TOKEN` | npm Trusted Publishing — see below |

**Both registries share a bootstrap wrinkle**: a trusted publisher is configured in
*an existing package's settings*, so the very first publish must be manual. That is
`cargo publish` once from your machine (needs `cargo login`), and one
`npm publish --access public`. Configure trusted publishing after, and CI is
tokenless from the second release on — for crates.io at least; see the `dist` OIDC
gap below for npm.

#### npm Trusted Publishing

Requirements: **npm CLI ≥ 11.5.1**, **Node ≥ 22.14.0**, and `id-token: write` in the
workflow's `permissions`. `setup-node` does not guarantee a new enough npm on its own —
upgrade it explicitly in the job:

```yaml
permissions:
  id-token: write
  contents: read
steps:
  - uses: actions/setup-node@v4
    with: { node-version: "22" }
  - run: npm install -g npm@latest
```

Provenance attestations are generated automatically — no `--provenance` flag.

**Two wrinkles to plan around:**

1. **Bootstrapping.** A trusted publisher is configured in *package settings on
   npmjs.com*, so the package must already exist. The first publish is therefore
   manual, from your machine — and, per the section above, only *after* the GitHub
   Release the package downloads from exists:

   ```sh
   npm publish --access public ./target/distrib/keb-npm-package
   ```

2. **`dist` 0.32.0 does not speak OIDC — confirmed, not speculation.** The generated
   `publish-npm` job authenticates with `NODE_AUTH_TOKEN: ${{ secrets.NPM_TOKEN }}`,
   and the workflow's only `permissions` block is `contents: write` — no
   `id-token: write` anywhere.

   Three ways forward, in order of preference:

   | Option | Cost |
   |---|---|
   | **Granular npm token scoped to `@frycz`**, short expiry, as `NPM_TOKEN` | One secret to rotate. Not what npm's warning is about — that targets account-wide *classic* tokens. |
   | Patch the generated workflow: add `id-token: write` to `publish-npm`, upgrade npm to ≥ 11.5.1, drop `NODE_AUTH_TOKEN` | Fragile — `dist generate` overwrites the file, and CI checks that it is in sync. |
   | Drop `npm` from `publish-jobs` and publish npm by hand | Loses the one-tag property for npm only. |

   The granular token is the pragmatic choice until `dist` ships OIDC support.

   One thing it already gets right: the job runs `npm publish --access public`, so the
   scoped-package trap above is handled for you.

Refs: [npm trusted publishers](https://docs.npmjs.com/trusted-publishers/) ·
[GA changelog](https://github.blog/changelog/2025-07-31-npm-trusted-publishing-with-oidc-is-generally-available/)

## Cargo.toml

`cargo publish` refuses without `description` and a license. It warns on missing
`repository` and `readme`. Fill all of it — the crates.io page and docs.rs build are
generated from this.

```toml
[package]
name         = "keb"
version      = "0.0.1"
edition      = "2021"
description  = "Rename files to kebab case, safely and idempotently"
license      = "MIT OR Apache-2.0"
repository   = "https://github.com/<user>/keb"
homepage     = "https://github.com/<user>/keb"
readme       = "README.md"
keywords     = ["kebab-case", "rename", "filename", "slug", "cli"]
categories   = ["command-line-utilities", "filesystem", "text-processing"]
exclude      = ["cases.md", "publish.md", ".github/", "tests/fixtures/"]

[lib]
name = "keb"
path = "src/lib.rs"

[[bin]]
name              = "keb"
path              = "src/main.rs"
required-features = ["cli"]

[features]
default = ["cli"]
cli     = ["dep:clap", "dep:walkdir", "dep:rustix"]
```

The `lib` / `bin` split is the architecture from `cases.md` made physical: `lib.rs`
is the pure `String → String` transform (§1–5, §9–11), `main.rs` is clap plus the
filesystem layer (§6–7, §12), and `main.rs` consumes the library exactly as an
external crate would. Feature-gating the CLI deps means library consumers get the
transform without the filesystem stack:

```sh
cargo add keb --no-default-features
```

`keywords` is capped at 5 on crates.io. `exclude` keeps the spec docs and fixtures
out of the published tarball.

## cargo-dist

The tool that generates everything. **The crate is `cargo-dist`; the installed binary
is `dist`** — `cargo dist …` does not work on 0.32.0.

```sh
cargo install cargo-dist --locked --version 0.32.0   # ~2 min, builds from source
dist init --yes
```

`dist init` is interactive by default; `--yes` accepts whatever is already in
`[workspace.metadata.dist]`, so pre-writing the config below and then running it is
the reproducible path. It runs `dist generate` at the end, producing
`.github/workflows/release.yml`.

Config, in `Cargo.toml`:

```toml
[workspace.metadata.dist]
cargo-dist-version = "0.32.0"
ci                 = "github"
installers         = ["shell", "powershell", "npm", "homebrew"]
tap                = "frycz/homebrew-tap"
npm-scope          = "@frycz"
publish-jobs       = ["homebrew", "npm"]
targets = [
  "aarch64-apple-darwin",
  "aarch64-unknown-linux-gnu",
  "x86_64-apple-darwin",
  "x86_64-unknown-linux-gnu",
  "x86_64-pc-windows-msvc",
]
install-path    = "CARGO_HOME"
install-updater = false

[profile.dist]
inherits = "release"
```

`dist` rewrites this block with its own comments and canonical ordering on `init`,
so do not hand-format it. The generated workflow is checked into the repo and CI
verifies it is in sync — after any config change, re-run `dist generate` and commit.

### How the npm side works

**Verified against `dist` 0.32.0 output, not assumed.** `dist` does *not* use the
esbuild-style layout of one wrapper plus N per-platform packages joined by
`optionalDependencies`. It emits **a single package** with a `postinstall` script that
downloads the right binary from the GitHub Release at install time:

```jsonc
// @frycz/keb — the whole thing, one package
{
  "name": "@frycz/keb",
  "version": "0.0.1",
  "bin": { "keb": "run-keb.js" },        // ← binary is `keb`, regardless of scope
  "scripts": { "postinstall": "node ./install.js" },
  "artifactDownloadUrls": [
    "https://github.com/frycz/keb/releases/download/v0.0.1"
  ],
  "supportedPlatforms": { /* target triple -> artifact name */ }
}
```

Two consequences that drive the release order:

1. **Only one npm package exists.** Not six. The "six manual first-publishes" figure
   in an earlier draft of this document was wrong.
2. **The GitHub Release must exist before the npm package is usable.** `install.js`
   fetches `…/releases/download/v<version>/keb-<target>.tar.xz` on every install, so
   publishing to npm before tagging produces a package that fails `postinstall` for
   every user. **npm is last, never first.**

The version in `artifactDownloadUrls` is baked in at build time, which is why the npm
package must be rebuilt per release and cannot be published ahead of the tag.

> **Scoped packages default to private** — a first publish without
> `--access public` fails with `402 Payment Required` on a free account. The
> generated `publish-npm` job already passes the flag; only a by-hand
> `npm publish` needs it added.

## Rehearse on a stub — before writing the real thing

The single most valuable step, and the one people skip.

Cross-compilation, macOS signing, the tap token, and the npm platform-package wiring
all break in their own ways, entirely unrelated to the transform. Debugging them
against a hello-world is ten minutes. Debugging them on launch day, while also
holding a Unicode bug, is not.

```sh
cargo new keb --lib
# stub lib.rs + main.rs, Cargo.toml metadata as above
cargo publish --dry-run
cargo package --list          # ← read this. anything not gitignored can be swept in
cargo publish                 # 0.0.1
cargo dist init && cargo dist generate
git commit -am "release plumbing" && git push
git tag v0.0.1 && git push --tags
```

The tag produces the six npm packages as build artifacts. **Publish them by hand
this once**, then configure a trusted publisher on each at
`npmjs.com/package/@frycz/<name>/access` — after which CI publishes them via OIDC and
no `NPM_TOKEN` is ever needed:

```sh
npm publish --access public   # × 6: wrapper + 5 platform packages
```

Then verify every channel actually lit up:

```sh
brew install <user>/tap/keb && keb --version
npx @frycz/keb@0.0.1 --version
cargo install keb --version 0.0.1
curl -sSf https://github.com/<user>/keb/releases/download/v0.0.1/keb-installer.sh | sh
```

Start at `0.0.1` precisely so burning a version or two on plumbing costs nothing —
and re-tag `v0.0.2` to confirm the OIDC path works now that the packages exist. That
second tag is the real test of the steady-state release, and it is cheap here.

## Release flow, thereafter

```sh
# 1. version bump in Cargo.toml (and npm package version if not derived)
# 2. update CHANGELOG.md
cargo test && cargo clippy -- -D warnings
cargo publish --dry-run
git commit -am "release: v0.1.0"
git tag v0.1.0
git push && git push --tags
```

CI does the rest. Watch the Actions run; a failure partway through can leave one
channel published and another not — see Recovery.

**`release-plz`** automates the version bump, changelog, and tag off conventional
commits, and opens a release PR. Worth adding once the cadence is more than
occasional.

## Immutability — the part that bites

**crates.io publishes cannot be undone.** A version number can never be reused, and
the tarball stays downloadable forever.

- `cargo yank --version 0.1.0` stops *new* dependents from resolving to it. It does
  **not** delete anything, and existing `Cargo.lock` files keep working. It is a
  signal, not a removal.
- Deletion requires emailing the crates.io team and is reserved for genuine
  emergencies (leaked secrets, legal).

npm is slightly softer — `npm unpublish` works within 72 hours if nothing depends on
the package — but do not plan around it. `npm deprecate @frycz/keb@0.1.0 "message"`
is the normal tool.

Homebrew is the forgiving one: the tap is a git repo, so a bad formula is fixed by
pushing a correction.

Therefore, before *every* `cargo publish`:

```sh
cargo package --list   # exactly what ships, nothing more
cargo publish --dry-run
```

## Recovery

| Failure | Fix |
|---|---|
| CI failed after `cargo publish` succeeded | Do **not** retag. Bump to the next patch and re-release; the partial version is spent. |
| Bad formula in the tap | Push a corrected `.rb`. No version burned. |
| Bad npm publish | `npm deprecate`, publish a patch. |
| Bad crates.io publish | `cargo yank`, publish a patch. |
| Tap push rejected (403) | `HOMEBREW_TAP_TOKEN` missing, expired, or lacking write scope on the tap repo. |
| npm 403 in CI | Token is not an *automation* token; classic tokens hit the 2FA prompt. |
| npm 402 Payment Required | Scoped package published without `access: public`. |

## Later, optional

- **homebrew-core** (`brew install keb`, no tap prefix) — PR to `Homebrew/homebrew-core`
  once there is visible adoption. The notability bar is judged on stars/forks, not
  quality. Note that core builds from source and makes its own bottles, unlike a tap
  which ships your prebuilt binaries.
- **Distro packages** — Debian, Fedora, nixpkgs, AUR. All separately gated, all
  later-stage.
- **docs.rs** — automatic on `cargo publish`, no action needed. `///` comments become
  the reference page, and doctests in them make the `cases.md` matrix executable.
